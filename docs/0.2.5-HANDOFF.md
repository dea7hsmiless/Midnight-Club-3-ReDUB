## 1. What 0.2.5 has to be

Midnight Club 3: DUB Edition Remix, recompiled, shipping on **Windows, Linux,
Android and iOS**, with online play:

- **Online is on by default**; turned off only through menus, never by editing
  a file by hand. Settings file must be created automatically at boot.
- The main menu's fourth item reads **Online**; inside it the two items read
  **Free Roam** and **Online Race**. No "Xbox", no "Live", no "System Link", no
  **"relay"** anywhere in the UI (code comments and logs are fine).
- **Rooms are numbers, chosen in game** (in the menu, not the launcher), 0..255,
  **8 players per room**. Players who pick the same number meet.
- **Matchmaking** exists (find-a-room), and the UI should show **how full** a
  room is.
- Everything ships in 0.2.5. iOS is the critical path (the user's only test
  device is an iPhone).

User preferences worth keeping: short answers, no long tables unless asked;
test one thing at a time; nothing pushed without explicit instruction.

## 7. The blockers

### 7.1 Free Roam **freezes** — the release blocker

Symptom: pressing Online → Free Roam freezes the game (seen on iPhone and PC).
No crash event; the window stops updating.

**Measured cause** (from a frozen instance's log): the emulated GPU's
push-buffer executor is waiting for the guest's driver to acknowledge a trap and
the guest never does, so it re-raises the interrupt for ever:

```
[PB] NOP(254280001) trap still pending after 2 s (PMC_INTR 00001000 EN 00000001)
```
repeating every ~2 s, thousands of times. Source:
`xboxrecomp/src/kernel/nv2a_pb_exec.c`, `trap_deliver_hooked()` (~line 4100): it
sets `PGRAPH_INTR`/`PMC_INTR` and spins on `s_trap_taken`, which the guest sets
when it takes the trap. If the guest is blocked elsewhere with interrupts held
off, this spins for ever.

So the freeze is **renderer/guest-side, not network** — the roam code is
innocent (races work; the roam session alone did not produce it).

**Not deterministic**: many runs reached the city cleanly (frames captured), one
run froze after `cruise: requested`, and the trigger correlates with entering
Free Roam (Arcade → loading → city).

**SOLVED, with one thing traded back (23 Nov, late).** The iPhone log was the
key: `cruise: requested` once, `Arcade opened from the frame hook` **never**, then
the trap spam. The front end's menu activation waits for the item to change the
screen; the deferred version returned without doing so, so it spun in the UI
list walk (the hang dump above), holding the guest lock — hence no trap taken,
no frames. It froze on PC and iPhone for the same reason; my earlier "verified"
transition used a hook that called the item from the frame loop and never
touched the activation path.

Fixed by making the item change the screen **synchronously** again, as the game's
own items do (`sub_00180160` → `sub_0018C530_gen()`). Verified through the real
press path (walker stepping onto the Online item and pressing A):

```
[ONLINE] cruise: requested
[ONLINE] cruise: Arcade opened synchronously
[AUTOSTART] 91.5s in game: stopped        ← the cruise is running
```

No trap spam, no hang. **The price is the original glitch**: the Online screen's
panel is left drawn over the next screen (doubled text over the MC3 logo, then
over the loading screen) because that screen is never torn down. Next step for
that is to back out of the Online screen first (the same thing its B button
does) and then call the Arcade callback, both synchronously — that keeps the
activation satisfied and gives the front end a chance to remove the panel.

**Root cause, measured (hang dump, 23 Nov, Windows build 15:4x).** The hang
watch dumped the guest thread inside a **linked-list walk** with the guest lock
held:

```
guest thread 8304:
  sub_002030B0   loc_002030D0:  while (node->field19 == 0) node = node->next;
  sub_00201990   (game_vtable, thiscall)
  sub_002071C0
  sub_0020A020
  sub_00160B90
  sub_00180350   (game_ui: the Online screen's own update)
```

A cyclic or corrupt list makes that loop eternal, and because the guest thread
holds the guest lock, the guest's interrupt thread never runs: the GPU trap is
never taken, the push-buffer executor re-raises `PMC_INTR` for ever, and no frame
is presented. One bug explains both the freeze and the trap spam.

The frozen instance's log also shows the recent indirect calls ending in
`00180160` (the Online screen's Free Roam item) and `NV2A USER PUT=00714C28
GET=00714BE0` (the push buffer stopped moving). It froze on a build **without**
the online rows, so the rows are innocent.

Likely trigger (hypothesis): the deferred screen change (`online_cruise_pass`,
top of the next frame) runs while the front end's UI object list for the Online
screen is still being built, and leaves that list cyclic. Test by deferring the
same call further out (two or three frames later, or from the input path
`sub_0018D590` instead of the frame hook) and re-running this repro.

**Next experiments, in order**
1. Reproduce with `MC3_HANG_SECS=5` *actually in the settings file* (it must be
   in `mcdub3remix_env.txt` beside the exe; the watcher prints
   `[hang] watching: …` when armed) and read the dump: the guest's registers,
   stack and recent indirect calls. That names what the guest is waiting on.
   `C:\Users\Donte\AppData\Local\Temp\opencode\freeze1.err.txt` was the last
   attempt — it had not frozen yet when the session ended.
2. Check whether the same freeze happens on the **release build**
   (`…\build-windows-x86_64\dist\mcdub3remix.exe`, 13:51) and on **Arcade →
   Cruise** (offline path, same city). If offline cruise also freezes, the roam
   code is fully exonerated and it is the emulator's loading/GPU path.
3. Look for the fence/vblank wait: `src/main.c`'s hang dump already prints
   `MC3_PB_STATE` (`0x003ECAF0 + 0x2C/0x30`, `+0x1DCC`) — the push-buffer state
   and the time last handed out. A guest stuck in D3D's `BlockOnTime`
   (`sub_003DF4D0`) points at the fence path (`MC3_FENCE_FIX` is on by default;
   `MC3_FLIP_PACE`, `MC3_TRAP_HOOK` exist as comparison switches).
4. If it cannot be root-caused quickly: the pragmatic fallback is to **take the
   trap on the engine's behalf after a timeout** in `trap_deliver_hooked()`
   (set `s_trap_taken`, log loudly, continue). That turns a permanent freeze
   into a possible visual glitch. Test it on a long free-roam session before
   believing it.

**Do not** ship 0.2.5 with this unresolved: free roam is the feature.

### 7.2 The room rows cannot live on the Online screen

Measured: the Online screen is a fixed two-slot movie (`Free Roam`,
`Online Race`). Its list reports **0 rows**, and rows appended to it are **added
but never drawn** (screenshot evidence). An earlier attempt attached them to the
**profile screen's** list instead (which has 2 rows), overwriting the profile
names and doubling the rows — that path is now disarmed
(`net_rows_arm()` has no callers; `network_rows_pass()` returns immediately).

The user asked for the rows "in the free roam section". The only ways there:
- put the room in the `Free Roam` label (the slot is 9 characters — no room for
  a count), or
- build a dedicated page (reusing the Options screen's list as a canvas, with a
  visible flash behind it and B intercepted), which is a new screen to design
  and verify on four platforms.

Current state: rows are on the **Port Options** page, with counts. That is what
works today.

### 7.3 The rare crash

`mcdub3remix.exe` has crashed a handful of times over two days at different
offsets (`0xe2e246`, `0x137cd48`, `0x15d9fab`, `0x1bdc42f`, `0x1be11`). The
14:09 one symbolises to `sub_002ED6F2 + 0xb8` (a guest allocator/object helper,
bad guest pointer) using `work-remix/build-windows-x86_64/mcdub3.map`. No repro.

**How to symbolise**: `python …\Temp\opencode\map_link2.py` relinks the current
objects with `-Wl,-Map=mcdub3.map` (same layout, so addresses match the exe),
then `python …\Temp\opencode\sym.py` maps a fault offset to `sub_XXXX`. Guest
addresses in logs can be read directly against `work-remix/gen/recomp_*.c`.

## 9. Traps that cost time here

- **Stale builds**: always string-verify the artifact.
- **The Online screen has no list**; do not append rows to it (§7.2).
- **The autostart walker's pad walks are unreliable** on pages that paginate
  (the Options screen's list page changes under presses). Firing a row's event
  through `sub_00163830` only works from the game's own input path, not from the
  frame hook. `mc3_menu_debug_dump()` prints the list words if you need to see
  the cursor.
- **`MC3_HANG_SECS` must be in the settings file** (or the real environment) and
  the watcher confirms itself with `[hang] watching: …`.
- **Windows log location**: `mcdub3remix_log.txt` beside the exe when launched
  from Explorer; `…\work-remix\logs\windows_run_<time>.log` when the launcher
  starts it; nothing when the game inherits a console or its stdio is redirected.
- **The iPhone log**: `Documents/mcdub3remix-launch.log` in the app's Files
  folder.
- **This machine is slow and shared**: boot is 60–210 s, two heavy builds at once
  make runs look hung, and a black window is usually the intro movie.
- **`windows_port_setting_label` returns void** (use `port_online_label` for the
  shared labels); `port_rows[]` is 32 entries, ids 24/25.
