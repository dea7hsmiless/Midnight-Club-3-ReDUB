## 0. Final state of this build (supersedes §1 below)

- **Free Roam is deferred to 0.2.6.** The Online screen's first item reads
  **`LINK: OFF`** (the screen is a fixed two-slot movie and the rename slot holds
  nine characters, so a strikethrough is not possible; "LINK: OFF" is the
  indicator). `sub_00180160` is inert: it logs "Free Roam is not in 0.2.5" and
  returns. Its Options rows (ROOM / FIND A ROOM) were removed; SHARPENING and HUD
  TEXTURES returned to the desktop Options page.
- **The race room picker is now the launcher's job.** Rooms are settled before
  the game starts, and the in-game page is dormant (`MC3_RACE_PAGE=1` turns it
  back on for 0.2.6). The rule is simple: **room 0 = anyone online**; rooms
  1..255 are separate groups, eight players each (the relay's own cap).
- **Auto-match:** with no `MC3_ROAM_ROOM`, the game asks the relay for the
  fullest room with a free slot and joins it (`[ROAM] auto-matched to room N`).
  So two people who just launch land together without doing anything.
  `MC3_ROAM_AUTO=0` disables it; a pinned room wins.
- **Launcher Online page:** live server/rooms/players/status over UDP
  (`MC3Q` census, `MC3P` roster), **Join a friend** (writes the room and
  launches), **Invite friends** (copies a `redub://room/N` link). The launcher
  registers `redub://` for the current user at startup
  (`HKCU\Software\Classes\redub`), and `ReDUB Launcher.exe --online` opens the
  page directly. A room change needs the game closed: settings are read at
  boot, and the page says so.
- **Launcher Online page is shared code, not three UIs.** `ui/online.html`
  (ES5, no framework) is the page; each shell hosts it and answers its calls.
  Windows hosts it in the WinForms `WebBrowser` (`window.external.redubCall`,
  `OnlineShell`), Android in a `WebView` (`@JavascriptInterface ReDUBAndroid`,
  `assets/ui/online.html`). Both are built and verified. iOS
  (`ios_launcher.m`, `WKWebView`) and Linux (the shipped launcher is a
  third-party config-driven binary) do **not** have the page yet — their 0.2.5
  builds carry the game changes only.
- **0.2.5 artifacts** (release folder, `SHA256SUMS.txt`, 9 entries):
  `ReDUB-0.2.5-Windows-x86_64.zip`, `ReDUB-0.2.5-x86_64.AppImage`,

- **Relay** now answers `MC3P` with a roster (`MC3PLAYERS 1 <n>` then one
  `room|status|name` line per player; status is RC_ST_*: 0 menus, 1 loading,

  does. Deployed to the VPS and confirmed answering.
- **Online Race is the online mode:** main menu -> Online -> Online Race ->

## 1. What 0.2.5 has to be

Midnight Club 3: DUB Edition Remix, recompiled, shipping on **Windows, Linux,
Android and iOS**, with online play:

- **Online is on by default**; turned off only through menus, never by editing

  **8 players per room**. Players who pick the same number meet.
- **Matchmaking** exists (find-a-room), and the UI should show **how full** a
  room is.
- Everything ships in 0.2.5. iOS is the critical path (the user's only test
  device is an iPhone).

User preferences worth keeping: short answers, no long tables unless asked;
test one thing at a time; nothing pushed without explicit instruction.

## 7. The blockers

### 7.1 Free Roam froze — fixed in `914af7f`

Symptom: pressing Online → Free Roam froze the game (seen on iPhone and PC).
No crash event; the window stops updating.

**RESOLVED.** The callback itself was the bug: `sub_00180160` returned
**without consuming its guest return address**, so the caller resumed on a
shifted stack, dispatched a garbage pointer, and the front end spun in a UI list
walk holding the guest lock (the dump below). It now does `g_esp += 4` on both
paths, and the item opens the dedicated Free Roam setup page
(`free_roam_setup_enter`) instead of Arcade. `tools/test_online_abi.py` fails
without the return.

Verified live on Windows: the setup page opens and draws for minutes with no
trap spam and no hang dump. An earlier synchronous `sub_0018C530_gen()` call in
the same callback masked the symptom from a different angle and has been
removed. Start now goes to the Cruise loader directly
(`free_roam_start_cruise`); that path is unit-tested but still needs the device
pass.

**Measured cause** (from a frozen instance's log): the emulated GPU's
push-buffer executor is waiting for the guest's driver to acknowledge a trap and
the guest never does, so it re-raises the interrupt for ever:

```
[PB] NOP(254280001) trap still pending after 2 s (PMC_INTR 00001000 EN 00000001)
```
repeating every ~2 s, thousands of times. Source:
`xboxrecomp/src/kernel/nv2a_pb_exec.c`, `trap_deliver_hooked()` (~line 4100): it
sets `PGRAPH_INTR`/`PMC_INTR` and spins on `s_trap_taken`, which the guest sets
when it takes the trap. If the guest is blocked elsewhere with interrupts held
off, this spins for ever.

So the freeze is **renderer/guest-side, not network** — the roam code is
innocent (races work; the roam session alone did not produce it).

**Not deterministic**: many runs reached the city cleanly (frames captured), one
run froze after `cruise: requested`, and the trigger correlates with entering
Free Roam (Arcade → loading → city).

**Root cause, measured (hang dump, 23 Nov, Windows build 15:4x).** The hang
watch dumped the guest thread inside a **linked-list walk** with the guest lock
held:

```
guest thread 8304:
  sub_002030B0   loc_002030D0:  while (node->field19 == 0) node = node->next;
  sub_00201990   (game_vtable, thiscall)
  sub_002071C0
  sub_0020A020
  sub_00160B90
  sub_00180350   (game_ui: the Online screen's own update)
```

A cyclic or corrupt list makes that loop eternal, and because the guest thread
holds the guest lock, the guest's interrupt thread never runs: the GPU trap is
never taken, the push-buffer executor re-raises `PMC_INTR` for ever, and no frame
is presented. One bug explains both the freeze and the trap spam.

The frozen instance's log also shows the recent indirect calls ending in
`00180160` (the Online screen's Free Roam item) and `NV2A USER PUT=00714C28
GET=00714BE0` (the push buffer stopped moving). It froze on a build **without**
the online rows, so the rows are innocent.

The shifted return address is what corrupts the list: the callback's caller
resumes on a frame four bytes off and follows a garbage pointer into the walk
above. (The older hypothesis — a deferred screen change racing the UI list —
described the same loop but not its cause; that code is gone.)

**Do not** ship a Free Roam build without `test_online_abi.py` passing: the
return-stack check is what catches this class of bug.

## 9. Traps that cost time here

- **Stale builds**: always string-verify the artifact.
- **The Online screen has no list**; do not append rows to it (§7.2).
- **The autostart walker's pad walks are unreliable** on pages that paginate
  (the Options screen's list page changes under presses). Firing a row's event
  through `sub_00163830` only works from the game's own input path, not from the
  frame hook. `mc3_menu_debug_dump()` prints the list words if you need to see
  the cursor.
- **`MC3_HANG_SECS` must be in the settings file** (or the real environment) and
  the watcher confirms itself with `[hang] watching: …`.
- **Windows log location**: `mcdub3remix_log.txt` beside the exe when launched
  from Explorer; `…\work-remix\logs\windows_run_<time>.log` when the launcher
  starts it; nothing when the game inherits a console or its stdio is redirected.
- **The iPhone log**: `Documents/mcdub3remix-launch.log` in the app's Files
  folder.
- **This machine is slow and shared**: boot is 60–210 s, two heavy builds at once
  make runs look hung, and a black window is usually the intro movie.
- **`windows_port_setting_label` returns void** (use `port_online_label` for the
  shared labels); `port_rows[]` is 32 entries, ids 24/25.
