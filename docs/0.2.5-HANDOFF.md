## 0. Final state of this build (supersedes §1 below)

- **Free Roam is deferred to 0.2.6.** The Online screen's first item reads
  **`LINK: OFF`** (the screen is a fixed two-slot movie and the rename slot holds

  returns. Its Options rows (ROOM / FIND A ROOM) were removed; SHARPENING and HUD

- **The race room picker is now the launcher's job.** Rooms are settled before
  the game starts, and the in-game page is dormant (`MC3_RACE_PAGE=1` turns it
  back on for 0.2.6). The rule is simple: **room 0 = anyone online**; rooms
  1..255 are separate groups, eight players each (the relay's own cap).
- **Auto-match:** with no `MC3_ROAM_ROOM`, the game asks the relay for the
  fullest room with a free slot and joins it (`[ROAM] auto-matched to room N`).
  So two people who just launch land together without doing anything.
  `MC3_ROAM_AUTO=0` disables it; a pinned room wins.
- **Launcher Online page:** live server/rooms/players/status over UDP

  launches), **Invite friends** (copies a `redub://room/N` link). The launcher
  registers `redub://` for the current user at startup
  (`HKCU\Software\Classes\redub`), and `ReDUB Launcher.exe --online` opens the
  page directly. A room change needs the game closed: settings are read at
  boot, and the page says so.
- **Launcher Online page is shared code, not three UIs.** `ui/online.html`
  (ES5, no framework) is the page; each shell hosts it and answers its calls.
  Windows hosts it in the WinForms `WebBrowser` (`window.external.redubCall`,

## 7. The blockers

### 7.1 Free Roam froze — fixed in `914af7f`

Symptom: pressing Online → Free Roam froze the game (seen on iPhone and PC).
No crash event; the window stops updating.

**RESOLVED.** The callback itself was the bug: `sub_00180160` returned
**without consuming its guest return address**, so the caller resumed on a
shifted stack, dispatched a garbage pointer, and the front end spun in a UI list
walk holding the guest lock (the dump below). It now does `g_esp += 4` on both
paths, and the item opens the dedicated Free Roam setup page
(`free_roam_setup_enter`) instead of Arcade. `tools/test_online_abi.py` fails
without the return.

Verified live on Windows: the setup page opens and draws for minutes with no
trap spam and no hang dump. An earlier synchronous `sub_0018C530_gen()` call in
the same callback masked the symptom from a different angle and has been
removed. Start now goes to the Cruise loader directly
(`free_roam_start_cruise`); that path is unit-tested but still needs the device
pass.

**Measured cause** (from a frozen instance's log): the emulated GPU's
push-buffer executor is waiting for the guest's driver to acknowledge a trap and
the guest never does, so it re-raises the interrupt for ever:

```
[PB] NOP(254280001) trap still pending after 2 s (PMC_INTR 00001000 EN 00000001)
```
repeating every ~2 s, thousands of times. Source:
`xboxrecomp/src/kernel/nv2a_pb_exec.c`, `trap_deliver_hooked()` (~line 4100): it
sets `PGRAPH_INTR`/`PMC_INTR` and spins on `s_trap_taken`, which the guest sets
when it takes the trap. If the guest is blocked elsewhere with interrupts held
off, this spins for ever.

So the freeze is **renderer/guest-side, not network** — the roam code is
innocent (races work; the roam session alone did not produce it).

**Not deterministic**: many runs reached the city cleanly (frames captured), one
run froze after `cruise: requested`, and the trigger correlates with entering
Free Roam (Arcade → loading → city).

**Root cause, measured (hang dump, 23 Nov, Windows build 15:4x).** The hang
watch dumped the guest thread inside a **linked-list walk** with the guest lock
held:

```
guest thread 8304:
  sub_002030B0   loc_002030D0:  while (node->field19 == 0) node = node->next;
  sub_00201990   (game_vtable, thiscall)
  sub_002071C0
  sub_0020A020
  sub_00160B90
  sub_00180350   (game_ui: the Online screen's own update)
```

A cyclic or corrupt list makes that loop eternal, and because the guest thread
holds the guest lock, the guest's interrupt thread never runs: the GPU trap is
never taken, the push-buffer executor re-raises `PMC_INTR` for ever, and no frame
is presented. One bug explains both the freeze and the trap spam.

The frozen instance's log also shows the recent indirect calls ending in
`00180160` (the Online screen's Free Roam item) and `NV2A USER PUT=00714C28
GET=00714BE0` (the push buffer stopped moving). It froze on a build **without**
the online rows, so the rows are innocent.

The shifted return address is what corrupts the list: the callback's caller
resumes on a frame four bytes off and follows a garbage pointer into the walk
above. (The older hypothesis — a deferred screen change racing the UI list —
described the same loop but not its cause; that code is gone.)

**Do not** ship a Free Roam build without `test_online_abi.py` passing: the
return-stack check is what catches this class of bug.

## 11. Online diagnosis, 2026-11-24 (supersedes the online parts of section 7)

Added after the "0 rooms in the game while both clients are in room 22" report.
Everything here was measured on this machine; nothing is published.

### 11.1 The relay was never the problem

- The VPS relay forwards correctly. Run locally, `tools/mc3relay.py --port 47300
  --verbose` logged a member's HELLOs (`(1)`) and tunnel frames (`(11)`) being
  fanned out to the other room member.
- A synthetic third player (`%TEMP%\opencode\probe_room.py`) registered in room
  22 (`MC3ROOMS ... 22:2` -> `22:3`) and its frames were forwarded by the relay.
- The PC game logged **no** `[XNET] rx` line for them, even on a loopback relay.
  So the datagrams arrive and the *client* discards them before
  `xr_tunnel_recv()`; this is not a NAT, relay-deploy or firewall problem.

### 11.2 What the client does instead (root cause candidate)

Reproduced without a phone, twice:

1. Start the game against a **local** relay (47300), `MC3_ROAM_ROOM=22`,
   `XNET_TRACE=1`, `MC3_ONLINE=1`, `MC3_NETPLAY=1`.
2. It registers (`[relay] joined Player <id> ... room 1441792 (1 here)`).
3. About 30-60 s later, with the process still running and responsive, the game
   logs `[roam] no free-roam hub answers` and the relay reaps it:
   `[relay] gone Player <id> (0 here)` -> census `no rooms`.
4. `roam_core.c:1004` is the print: `st = !hub ? 0 : ...`; the client left hub
   mode because `hub_mode()` (`roam_core.c:592`) expires after `T_HUB_SILENT`
   when `hub_heard_us` was never set. The relay is a pure forwarder: it never
   answers a member's PING with a PONG (only strangers get one,
   `tools/mc3relay.py:281`) and never sends PEERS, so `hub_heard_us` stays 0.
5. Once the relay reaps the member, every later datagram is "not a player we
   know" (`mc3relay.py:336`) and is dropped -> the other client sees **0 rooms**
   even though both games are open.

This matches the user-visible symptom (room shows players for a short while,
then `no rooms`; a restart "fixes" it for another minute).

### 11.3 Why the probe's tunnel frames also vanished (client gate)

`roam_core.c:801` drops any non-HELLO datagram from an unknown sender, and a
HELLO only promotes a peer when `p->hears_us` is set, i.e. its `seen` list names
our own id (`roam_core.c:839-846`). A stranger's tunnel frames are therefore
discarded by design. This means: **to test transport, the probe must HELLO with
`flags=0x20` and `n_seen=1, seen=[game id]`**, then the tunnel frames should
reach `xr_tunnel_recv()` and print `[XNET] rx`. The script already does this

### 11.4 The "crash" is an exit hang, not a gameplay crash

Windows Event Viewer (11-24 06:41, 06:53, 09:09, 09:12, 09:24) reports

and was closed". `work-remix\logs\latest.log` ends with

09:09/09:12/09:24 entries are force-kills from this session; 06:41 and 06:53 are

after the window closes) or by finding the blocking join, and verify with

### 11.5 The fix, in order

1. **Keep hub mode alive under a relay** (client, smallest safe change):
   in `roam_core.c`, on any datagram accepted in relay mode, set
   `s->hub_heard_us = now` (the rentry is already at `roam_core.c:772` for hub
   lists; use the relay-receive path). `hub_mode()` then never expires while the
   relay is actually forwarding.
2. **Make the relay answer members**: in `tools/mc3relay.py`, reply PONG to any
   `T_PING` (not only `known is None`), so a non-relay hub deployment also
   reports life. Rebuild/redeploy with `tools/deploy_relay.sh` (it verifies with
   a joined player).
3. **Verify the HELLO cadence outside the cruise**: `roam_core.c:992` sends the
   hub HELLO every `T_HUB_HELLO` when `conf.hub_ip` is set; confirm `rc_tick()`
   is called from the host frame loop and not only from the cruise path, or a
   player sitting in the System Link menu is invisible to the relay. This is the
   difference between "reaped at 30 s" and "stays".
4. **Trace the drop reason**: extend `XNET_TRACE` so an arrived-but-undelivered
   tunnel frame prints why (unknown peer id, no socket for the port, queue full).
   Right now an rx that never reaches the callback is silent.
5. **Exit hang**: watchdog exit, then confirm with `MC3_HANG_SECS=5`.

### 11.8 Root cause found, fixed and verified (corrects 11.2)

11.2 named the right symptom (the client goes quiet and the relay reaps it) but
the wrong mechanism: the "no free-roam hub answers" line was a *symptom*, not
the cause. The defect is in the roam socket loop.

**The bug.** `roam_plat.c: plat_receive_all()` drains up to 64 datagrams with
`recvfrom()` after a single `select()` on a **blocking** socket. The select
guarantees one datagram, not 64. A relay only forwards, so a room with no
traffic sends nothing back: after the first stray/relayed datagram the thread
parks inside `recvfrom()` and never returns to `rc_tick()`. That stops HELLOs,
pings and peer timeouts, the relay reaps the player after 30 s, and the other
client sees **0 rooms** while both games are open. A restart "fixes" it for a
minute because the thread gets a fresh select() with no queued datagram.

**Proof.** The hang watcher's thread dump from the test run:

```
[HOSTSTACK] every thread's native stack (hang: no frame presented for 5s (frame 329))
[HOSTSTACK] thread 27324
  #4 plat_receive_all   (roam_plat.c)
```

Resolve the dump with the image base (`llvm-addr2line -e mcdub3remix.exe
0x140000000+rva`); without the base every frame prints `??`.

**Fixes in the tree (uncommitted):**

- `xboxrecomp/src/net/roam/roam_plat.c`: after `bind()`, set the socket
  non-blocking (`ioctlsocket(FIONBIO)` on Windows, `O_NONBLOCK` via `fcntl` on
  POSIX, `<fcntl.h>` added). The drain loop now returns to `rc_tick()` every
  10 ms, which is what keeps HELLOs and peer timeouts running.
- `xboxrecomp/src/net/roam/roam_core.c: rc_receive()`: a framed datagram from
  the configured relay counts as "hub alive" (`hub_heard_us = now`). A pure
  forwarder cannot otherwise satisfy `hub_mode()`'s `T_HUB_SILENT` timer, and
  the client prints "no free-roam hub answers" and stops trusting the room.

**Verified (local relay on 127.0.0.1:47300, room 22):**

- A lone game stayed in the census `MC3ROOMS 1 1 22:1` for the full 4 minutes
  with no `gone`; before the fix it was reaped in ~90-150 s.
- `%TEMP%\opencode\probe_room.py 127.0.0.1 47300 <game-id>` (HELLO with
  `flags=0x20` and `seen=[game id]`) produced, on the game:
  `[roam] Probe joined` and six
  `[XNET] rx 10.99.0.1:1000 -> 255.255.255.255:1000 24 bytes  01 37 18 00 ...`
  So relay -> client -> `xr_tunnel_recv()` -> guest queue works end to end.

**What this does and does not prove.** The 24-byte System Link discovery
broadcast now reaches the guest. If the in-game lobby still lists no room with
a real phone, the remaining bug is guest-side content/session handling (the
session-directory work), not NAT, the relay or the client transport.

**The relay PONG idea in 11.5(2) is unnecessary** and was not done: the client
drops datagrams from unknown senders, so a relay-sent PONG would not set
`hub_heard_us` anyway. 11.5(3) is moot (the tick thread was parked, not the
HELLO cadence). 11.5(4) and (5) are still open.

**Still open:** the Windows exit hang (11.4) and the release re-package. The
rebuilt game is `work-remix/build-windows-x86_64/mcdub3remix.exe`; the release
zip and `SHA256SUMS.txt` have not been touched since 06:54.
