# 0.2.5 backlog — what ships, what waits for 0.2.6

Written 2026-11-21. One list so nothing is lost between releases. The rule applied
throughout: **a feature ships when it is verified working, not when it is nearly done.**
Anything not verified is either left out or explicitly described as experimental and
opt-in.

### Deferred to 0.2.6: System Link (moved 2026-11-21)

System Link works — two instances, one creates a match, the other discovers and joins, both
lobbies agree, and they share a cruise with name tags. But **every one of those runs was two
copies on one machine over loopback.** That proves the emulated XNet layer is wired up
correctly; it does not prove two PCs on a real LAN can play.

Owner's call, and it matches the standard applied to online: a multiplayer claim needs a
second machine. So `MC3_NETPLAY=1` moves to the 0.2.6 list with the rest of multiplayer, and
0.2.5 ships with split-screen as its only multiplayer mode — which is genuinely local and
genuinely verified.

The code stays in the tree, working and opt-in.

### Not shipping: the online/free-roam feature

**Explicit decision (owner, 2026-11-21):** no online in 0.2.5 unless it is *full* online
with a server setup. It is not. What exists is direct peer-to-peer discovery on one LAN,
verified two-instance — no matchmaking, no rooms, no server, no NAT traversal,
no way for two players who are not on the same subnet to meet.

So `MC3_ROAM=1`, `MC3_ONLINE_SESSION=1` and `tools/mc3hub.py` stay **in the tree, off by
default, and undocumented in the release notes.** They are the foundation for the real
feature, not the feature.

What that means practically:

- The release notes say nothing about online. No "multiplayer" claim beyond System Link
  and split-screen, both of which are local and verified.
- The store listing's "Multiplayer" must not be read as online. It never should have been.
- The code stays because throwing away working transport, the remote-car pool and the
  pedestrian path would mean rebuilding it for 0.2.6.

## WAITS FOR 0.2.6

work: **a server.**

| 7 | Collisions with other players' cars | Remote cars are pass-through. Needs the game's own collision path, not a hack. |
| 8 | Pedestrian sync beyond ~15 m | Currently proximity-only (Option A). A real implementation needs the ghost path (`MC3_ROAM_AMBIENT_PEDGHOST`), which is implemented but inert and unverified. |

| 10 | Peer discovery across a restart | A restarted instance may not re-find the other without relaunching both. |

**Minimum bar to call it "online with a server":** two players on different networks, each
able to find and join the other's session through a server, with the other's car visible.
Nothing less ships under that name.

## Aspect ratio: should it change? (asked 2026-11-21)

**Short answer: the feature is fine; one document is wrong, and the value names are ugly.
Two small changes, no redesign.**

What exists, verified in the tree:

| Layer | State |
|---|---|
| Renderer | `nv2a_present.h`: `nv2a_present_rect()` letterboxes/pillarboxes/centres the picture. Used by both GL (`nv2a_gl.c:7378`) and Vulkan (`nv2a_vk.c:604`, `:3753`). |
| Launcher (Windows) | Real "Aspect ratio" row in `recomplauncher.json`: Auto (16:9) / 4:3 / Stretch, with help text. |
| In-game | Documented in `docs/PORT-OPTIONS-WINDOWS.md` as a Port Options row ("Display shape"). |

### The one thing that is actually wrong

**Nothing in the feature. One value name and one missing warning.**

My first draft of this section claimed the in-game Port Options row did not exist and that
commit `9348a84` was docs-only. **Both were wrong.** The commit added a real row in
`src/linux_settings.c` and `src/windows_settings.c`:

```c
case 8: display shape cycles auto -> 4:3 -> fill, saved to RECOMP_GL_ASPECT
if(id==8) "DISPLAY SHAPE: %s (RESTART)"
```

So there are **three** surfaces — renderer, launcher row, in-game row — and they agree on
the three values. The label even says `(RESTART)`, which correctly reflects the cached read.

What is left is cosmetic:

1. **`fill` should be `stretch`.** The labels say STRETCH and Stretch; the stored value is
   `fill`. It works, but a player editing their env file has to know that. Either accept both
   spellings or rename it.

2. **An unrecognised value silently means Auto.** `mode = ... : e && !strcmp(e,"4:3") ? 2 : 0`
   — so `RECOMP_GL_ASPECT=strech` (typo) gives 16:9 with no warning. A one-line warning is
   honest and costs nothing.

3. **The in-game row can only be changed in game, applied after a restart.** That is
   correct as designed and labelled, but it means the row exists mainly to *show* the
   current value. A live apply is possible (the cache is a `static` in a header-only
   function) but is a 0.2.6 change, not a 0.2.5 one.

### What I would *not* change

The letterbox behaviour itself is correct and subtle, and `nv2a_present.h` explains why: an
Xbox title renders a 4:3-sized buffer even on a widescreen TV, so the presenter has to widen
it, and MC3 specifically has a 768-pixel pitch with only 720 drawn — which the old "narrower
than 3:2" test got wrong, producing a 1.6:1 picture with 48 dead columns. That fix
(`lw` = drawn width, not pitch) should stay exactly as it is.

**Recommendation for 0.2.5:** ship as is. It is implemented on all three surfaces and
verified by reading the code paths; what it lacks is one on-screen confirmation, not work.
The two cosmetic items go on the 0.2.6 list.

## Open: a second, different intermittent freeze (movie playback)

Found while testing the fix below. **Not the same bug, not fixed.**

It happens while the intro movies play, and only with movies enabled — every clean run in
this session used `MC3_SKIP_MOVIES=hard`, which is why it took this long to see. Movies play
by default (`#MC3_SKIP_MOVIES=0` in the shipped env example), so every player takes this path.

Observed twice:

```
[WATCHDOG] hang: no frame presented for 12s (frame 208)
  #2  xbox_NtWaitForMultipleObjectsEx   kernel_sync.c:260
  #7  sub_0001725E  #8 sub_00017342  #9 sub_003ADBA0
  #10 sub_003AE090  #11 sub_003AE200  #12 sub_003ADA70_gen   <- BinkDoFrame's region
NV2A USER  PUT=0065E194 GET=0065E194      <- pushbuffer fully consumed, GPU idle
```

The pushbuffer is drained and the GPU idle, so this is **not** the desync bug: the guest
thread waits inside Bink, on Bink's own worker threads.

It is **intermittent**: a repeat run played all three movies (`rockstar.bik` 209 frames,
`sdlogo.bik` 122, `mc3intro.bik` 17) and reached the cruise in 55.6 s with no hang.

**Mitigation today:** `MC3_SKIP_MOVIES=hard` skips the movies entirely and was clean in every
run — but it removes the intros, so it is a workaround, not a fix.

**Next step:** the native decoder (`src/bink_native.c`, FFmpeg, on by default) feeds Bink; the
wait is on Bink's side. A progress timeout that forces the existing skip path
(`movie_skipped`, where `BinkDoFrame`/`BinkWait` return at once) would turn a hung movie into
a skipped one. Contained change, better than shipping with movies off.

### What the stack actually says (2026-11-22)

The guest is blocked in `sub_003ADBA0`, which is Bink's own thread-fetch helper:

```c
/* 0x003ADBA0, 59 bytes */
PUSH32(esp, -1);            /* INFINITE */
PUSH32(esp, 0);
PUSH32(esp, &array);        /* two handles: edi, esi */
PUSH32(esp, 2);             /* Count = 2 */
call sub_00017342           /* NtWaitForMultipleObjectsEx */
```

So Bink waits on **two of its own worker handles with an infinite timeout**. In
`xboxrecomp/src/kernel/kernel_sync.c`, `xbox_NtWaitForMultipleObjectsEx` passes that straight
to `WaitForMultipleObjectsEx` — **no recheck hook and no cap**. If one handle never signals,
that call never returns, and nothing in the port can intervene.

That is why a frame-progress watchdog cannot fix this: the watchdog thread runs, but the guest
is inside a host wait and our wrappers are never called again.

The fix has to bound that wait. Two candidates for 0.2.6:

1. **Cap infinite waits while a movie is open.** The port knows when a movie is open
   (`mc3_bink_native_open` / close in `src/bink_native.c`); expose that, and in
   `xbox_NtWaitForMultipleObjectsEx` use a finite timeout while it is true, returning
   STATUS_TIMEOUT so Bink's caller takes its error path. Contained, but it changes kernel
   semantics, so it needs a real reproduction to validate — not something to ship blind.
2. **Stop Bink owning threads at all.** Decode at Bink's entry points and never let its
   worker path run. Much larger, but removes the class of bug rather than the instance.

**Why it is not fixed in this pass:** it reproduced once in three runs. A change to kernel
wait semantics that cannot be validated against the bug is worse than a documented
workaround. `MC3_SKIP_MOVIES=hard` is the workaround, and the reporter's log tells us whether
their freeze is even this one.

**Test switch now in the tree (2026-11-22):** `MC3_MOVIE_WAIT_MS=2000` bounds INFINITE
multi-object waits in `xbox_NtWaitForMultipleObjectsEx` and logs the first few. Off by
default, so the shipped build is unchanged. The point is to have the reporter run with it:
if the hang disappears, the diagnosis is confirmed and the fix can be made unconditional;
if it does not, the wait was not the blocker and this line of investigation closes.

**This may be the reporter's freeze.** "Freezes on frame" fits a frozen movie frame, and
their build plays movies. Telling the two apart takes their `latest.log`: the desync freeze
shows `[PB] decode abort`, this one does not.

## The freeze fix (item 1) — what it was

Reproduced on a clean install, 60 FPS, cruise, no free roam:

```
[AUTOSTART]   55.3s in Cruise
[WATCHDOG] hang: no frame presented for 12s (frame 4453)
[HOSTSTACK] thread 29524
  #3  kdisp_wait
  #4  bridge_KeWaitForSingleObject
  #8  sub_004165A0_gen
  #9  sub_004165A0          recomp_manual.c:242
```

Permanent: one hang, frame count never advanced again. Exactly the reported shape —
"freezes on frame, have to kill it".

**Cause, in three parts:**

1. The pushbuffer walk lost the command stream and started reading zeros as command
   headers. `GET=003B9704 PUT=0062E528 word=00000000`, `words=4194305`.
2. Zeros decode as *valid* zero-count headers, so the `unknown` counter never rose — the
   only thing that caught it was a 16 MB word budget, several times a frame.
3. On abort it `break`s **without moving GET**, despite the file's own header comment
   saying GET should snap to PUT. So the next call resumed at the same desynced address,
   walked the same zeros, aborted again. It never executed another command — including the
   semaphore release the frame was waiting on:

```
[D3D] fence event still pending: GPU=000304FD target=00030531 lastRelease=000304FD
```

`lastRelease` is the *previous* frame's value. The target was in the discarded remainder.
XDK D3D waits on that value with no timeout.

**Fix, four parts:**

1. **Snap GET to PUT on abort**, as the comment always said and as a bad jump already does.
   The frame's remaining commands are lost; the stream is not.
2. **Detect the real signal: a run of zero words** (`PB_ZERO_RUN_MAX`, 256). Fires
   immediately instead of 16 MB later. In the original hang the abort was
   `word=00000000 words=4194305` — pure zeros, which is exactly this test.
3. **Publish the fence target when a wait began before a desync.** `nv2a_pb_note_desync()`
   bumps a counter; the fence recheck notices it changed under it and releases to the
   target. One frame is dropped instead of the session hanging.
4. **A test hook, `RECOMP_PB_DESYNC_AT_SEC=<n>`**, forces one abort n seconds in so the
   recovery path can be exercised without waiting for an intermittent freeze.

**Regression found and reverted (2026-11-21).** A fifth change cut the word budget from
4.2 M to 262 K on the theory that a long walk is a desync. Measured, that was wrong and it
*caused* a freeze:

```
[PB] decode abort: GET=00686D58 PUT=0068705C words=262561 zero_run=0
```

772 bytes apart, 262 K words walked, zero zeros — a healthy walk following jumps, aborted by
my cap. The aborts discarded real commands and the frame hung at boot frame 311, before the
test hook had even fired. The budget is back to 4.2 M; the zero-run test is what catches a
desync, in 256 words.

Same code is in v0.2.4a, so this is a fix for the build the user is on, not something new
in 0.2.5.

**Honest caveat:** the fence release is a judgement call — it declares "this fence is never
coming" after a desync. That is true when the release was in the discarded remainder, and
the alternative is waiting for ever. It is bounded to a wait that began *before* the desync,
so it cannot fire in a healthy frame.

### The same defect in the bad-jump path (found 2026-11-22)

The desync abort was not the only place that refused to move GET. A jump or call with a
target outside RAM went through `pb_bad_target()`, which returned 1 and was handled as:

```c
if (pb_bad_target(w, at, target, put)) { s_get=at; break; }
```

`s_get=at` is the position it was already at, so the next call read the same word, resynced
to the same address, and made no progress. Reproduced on a two-instance run at 18 cars:

```
[PB] bad target #4886500 0x2D181844 from word 0x2D181845 at 0x018405D0 (PUT 0x00763EEC); resync
[PB] bad target #4887500 0x2D181844 from word 0x2D181845 at 0x018405D0 (PUT 0x00763EEC); resync
[WATCHDOG] hang: no frame presented for 15s (frame 5987); guest esp=0x00F7FB2C
```

**4.88 million resyncs to one address**, frame count frozen. That is a permanent hang with a
perfectly clear signature, and it is a better candidate for the reported "freezes on frame"
than the desync path, because it does not depend on a zero-filled ring.

Both now go through one helper, `pb_drop_batch()`, which records the drop, bumps the desync
counter (so a waiting fence is released) and moves GET to PUT. One rule instead of two
half-fixes: **if the walk cannot continue, it must move.**

Note the print is rate-limited to every 100th, so 4.88 million resyncs is only ~48,000 log
lines — the log looks noisy but not pathological, which is why this hid for so long.
