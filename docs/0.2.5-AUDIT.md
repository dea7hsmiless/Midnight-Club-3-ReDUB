# 0.2.5 audit — what was wrong, what was fixed, what is still open

A read-only audit of the 0.2.5 changes (online rooms, matchmaking, the two new
options rows, the settings/online defaults) across the relay, the roam core,
the options UI and the four platform hosts. Every item below that says *fixed*
was reproduced (a failing test or a measured before/after) before the change.

## Rooms and matchmaking

| # | Problem | State |
|---|---------|-------|
| 1 | The relay's eight-player cap compared the **full room key**, city included. Nine or ten players could share "room 3" if they loaded different cities, and the census then advertised `3:9` — past the eight slots the game has. | fixed: a picked room number counts across cities; room 0 (the default, nobody picked one) stays per city |
| 2 | A known member could re-HELLO into a **full** room; the cap was only checked when a sender was first seen. | fixed |
| 3 | The census listed **every** room: 1440 bytes at 256 rooms. The client drops any answer of 512 bytes or more outright, so *Find a Room* silently did nothing on a busy server; between 40 and 511 bytes it saw only the first 32 rooms. | fixed both ends: the relay sends at most 32 rooms (busiest first, under 512 bytes), the client parses a long answer instead of discarding it |
| 4 | The census table was written on the receive thread and read on the game thread with no lock, and any host could answer it. | fixed: locked, and only the server that was asked may answer |
| 5 | *Find a Room* could read "SEARCHING..." for ever when no answer came, and could act on a census taken before the request. | fixed: a request clears the old answer, and six seconds without one clears the search and logs why |
| 6 | The ROOM row ignored the press direction and could show a room outside 0..255 that the D-pad cannot reach. | fixed |
| 7 | The relay had no total member cap, kept a flood-table entry per source address for ever, accepted HELLOs no client could ever decode (long/non-printable names, impossible `n_seen`), so eight such datagrams sealed a room for real players, and answered PINGs with an id no client accepts. | fixed |
| 8 | A garbage census answer erased a good one and was reported as fresh. | fixed |
| 8b | **Found during the in-game test, after the audit:** a player whose session stalls past the 30 s expiry (a cruise loading takes longer) was fetched, then reaped, then healed — and the heal read `self.members[sender]`, which raised `KeyError` on the receive path. That datagram, and that player's stream, were lost. | fixed (reap before the lookup, guarded re-fetch, regression test in `test_room_rules.py`) |

Tests: `tools/test_room_rules.py` (cap, census bounds, re-HELLO, a full
server), `tools/test_relay_live.py` (the relay as a process, two client
sockets, census), plus the existing `test_mc3relay.py`, `test_relay_guards.py`,
`test_mc3hub.py`.

## Free roam / System Link

| # | Problem | State |
|---|---------|-------|
| 9 | **Relay rooms could only ever hold one other player.** In relay mode every peer arrives from the relay's single address, and `rc_add_peer` looked peers up by address, found the previous player, and "restarted" (evicted) them for each new sender id. | fixed: in relay mode peers are found by sender id and take a free slot |
| 10 | A FAR part could write past `far_in`/`far` (13 parts x 20 entries = 260 for a 256 table) and the merge copied the overflow on; reachable from the hub address with a valid CRC. | fixed: each part must fit its own slice, the merge is clamped |
| 11 | The receive drain loop was unbounded, so a flood could keep `rc_tick` from ever running (no HELLOs, every peer times out). | fixed: 64 datagrams per wakeup |
| 12 | Datagrams arriving after shutdown re-added peers; a peer in another room kept its table slot and its HELLO traffic for ever. | fixed |
| 13 | A room change made in game was lost when online play stopped and started again in the same process: the room was saved to the file but the process environment still held the old value, and `roam_start` re-read that. | fixed: `roam_set_group` updates `MC3_ROAM_ROOM` too |

## Options page

| # | Problem | State |
|---|---------|-------|
| 14 | The page holds 16 rows and the desktop order had grown to **18** — the two online rows pushed BACK off the page (the list is a fixed array, so this also wrote past it). | fixed: 13 settings + ROOM + FIND A ROOM + BACK = 16, verified on screen: `[PORT] page 0: 16 rows, 16 slots \| ROOM: 5 \| FIND A ROOM` |
| 15 | iOS lost the row that opens the Advanced page (id 15) in the reordering, so every advanced setting (touch tuning, tilt, phone music) was unreachable. Android had lost controller vibration the same way. | fixed |
| 16 | One unchecked guest read in the front-end list walk (`count` read with an unvalidated column), and the label slack scan read up to 64 units past the range it had validated. On Windows the readable size was measured from the region base, not from the address asked about. | fixed |
| 17 | The title restore could blank the parent title when nothing had been saved. | fixed |

## Settings and defaults

| # | Problem | State |
|---|---------|-------|
| 18 | On Windows, settings were saved from two threads through **one temp path** (the guest thread's ROOM save and the window thread's queued changes), so one could rename a half-written file over the other. | fixed: serialised, one temp name per thread; a file that exists but cannot be read is never rewritten over |
| 19 | iOS renamed the temp file without checking the write or the close, so a full disk committed a truncated settings file. | fixed |
| 20 | The settings file was created at boot on iOS only, and the online default (`MC3_ROAM_JOIN` + `MC3_NETPLAY`) applied on iOS only — so Windows, Linux and Android shipped **offline by default** while the requirement says online is on unless turned off. | fixed on all four |
| 21 | A hand edit with a space before `=` or a quoted value worked on Windows/Linux and was silently ignored on iOS/Android. | fixed |
| 22 | A failed `SetWindowLongPtr` left a null WNDPROC to chain to. | fixed |

## Still open (not fixed here)

- **A rare crash on Windows, before the title screen.** Event log shows access
  violations on 11-21 (twice), 11-23 07:01/07:03 (twice) and once at 12:50
  during this audit, at different offsets, with no reproduction since (a run
  that looked black at first was the intro movie decoding under load). A link
  map is now produced by the audit tooling so the next one can be symbolised
  instead of guessed at.
- The **census cannot distinguish cities.** A player who picked room 3 but
  loaded another city is counted in "3:N" and cannot be met there. The room key
  deliberately carries the city, and free roam is per city; matchmaking can
  only send a player to a room number, not a city.
- **macOS** has no `windows_port_settings_attach` / label / change definitions
  (pre-existing); the Switch got stubs, macOS was not buildable here.
- The Port Options **page title** still reads "OPTIONS": the write is either
  into a field the Flash file redraws, or into a UTF-16 buffer. Cosmetic, and
  the save/restore is byte-exact either way.
- The switch's PING handling only answers an unknown sender (a member's ping is
  relayed so peers can measure each other).

## Verified with the real binary

- The game, started from a settings file that named the server and room 9,
  joined that room on a local relay: `joined ClientTest <id> room 589824`
  (589824 = 9 << 16), and stayed joined (a HELLO a second) with the relay's
  error output empty. Two of those runs, including one from a fresh settings
  file.

## Verified on screen

- The Options page builds with exactly 16 rows in 16 slots.
- `ROOM: 5` and `FIND A ROOM` render as the last two rows before BACK.
- The page shows 13 desktop settings plus the scroll arrow to those rows.

Not yet seen on screen: pressing ROOM live (the walker's cursor arithmetic on
the parent list is unreliable), and a two-device race through the relay.
